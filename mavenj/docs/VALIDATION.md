# MavenJ validation and acceptance evidence

Validation date: 2026-10-24. Local environment: macOS 26.5.1, Apple M5, 16 GiB RAM, Amazon Corretto 25.0.4.1 for the editor/build, with an installed Corretto 21 JDK for alternate-runtime and lifecycle tests. A clean macOS installation and an actual Java 17 runtime were not available. Java 17 source/API compatibility is tested separately from Java 17 runtime execution.

This document distinguishes an exercised fixture from general Maven build parity. Generated fixtures use public Java/JUnit dependencies and no proprietary projects. Native compilation, import, formatting and refactoring do not launch Maven; lifecycle tests deliberately launch the real distribution or a controlled wrapper fixture.

## Recorded runs

- Complete TurboJ root `verify` passed **462 tests**, with **0 failures, errors or skipped tests**, counting Surefire and Failsafe reports: MavenJ 58, editor core 91, app 114, worker 17, FormatJ 32, CommandJ 28, RefactorJ 114, TurboTest 3 and TurboJ CLI 5. MavenJ's 58 comprise core/resolution 27, workspace 24, CLI 3 and MCP 4. Reports are under each module's `target/surefire-reports` or `target/failsafe-reports` directory.
- Native integration focused suite: 47 tests passed in `target/maven-native-final-focused.log`: workspace transactions 19, Maven compilation 5, worker 17, real lifecycle parity 1, formatting controller 5. This is a targeted baseline, not a count for the complete TurboJ reactor.
- The subsequent regression suite passed **39 tests** in `target/maven-native-final-regressions.log`: toolchains 6, Java intelligence 20, Maven compilation 7, workspace compilation 3, Maven Auto Test controller 1, native/real-Maven parity 2. This verifies the independent-module semantic lookup, legacy read-only source attachment behavior, invalid-model execution guard, source/target 8 semantics and Auto Test generations. These suites overlap and their counts must not be added into a unique-test total.
- The final focused correction suite passed **44 tests** in `target/maven-native-publication-regressions.log`: MavenJ effective models/resolution 25, repository policy 2, toolchains 6, Maven compilation 8, Auto Test controller 1 and parity 2. It adds imported-snapshot-BOM invalidation, safe recovery after failed output publication/cancellation, and retention of an unchanged module's outstanding test failures.
- That full verification preceded one final Auto Test correction: removing cached reports when a module or its last test source disappears. The extended **11-generation** `MavenAutoTestControllerTest` then passed separately in `target/maven-autotest-pruning-regression.log`. This sequence is explicit: the root run does not claim to include the later pruning change, and the targeted run is not an additional unique test in the 462-test count.
- Actual Swing GUI smoke passed **25 checks**, including reactor import, native run, unsaved buffers, formatting, cross-module refactoring, POM preview/edit, project explorer, three themes, embedded dialogs, trust and explicit wrapper `validate`. It also enables Auto Test through CommandJ, edits Java, waits for native compilation and verifies one passing JUnit test from the current generation without launching Maven. The wrapper launch count remains zero during editing/formatting/refactoring/Auto Test and becomes one only for the requested real Maven `validate`. This final GUI run uses the packaged application after the pruning correction. The report is `app/target/maven-smoke/report.txt`; six screenshots are in that directory.
- Native versus explicit Maven lifecycle parity passed: `target/maven-native-lifecycle-parity.txt` records two passing JUnit tests in each path on the selected Java 21 JDK.
- Source/target 8 parity also passed: `target/maven-source-target8-parity.txt` records classfile version 52 and the same runtime result in the native compiler and an explicit current-JDK Maven compilation. It deliberately uses a newer platform API to distinguish source/target from `--release`.
- Performance runs and their raw data are documented in [PERFORMANCE.md](PERFORMANCE.md) and [native compiler/EDT measurements](../../benchmarks/results/MAVEN_NATIVE.md). The short JMH runs are observations, not product latency guarantees.

## Additional correctness and protocol checks

`PomEditsTest` and `PomFilesTest` cover comments, namespace prefixes, properties, CRLF, Unicode/UTF-16, BOM preservation, stale previews, symlink/root escapes and malformed/DTD-bearing XML. `XmlEditingTest` exercises actual editor highlighting, XML diagnostics and preservation of encoding on save. POM actions preview deliberate edits and leave unrelated formatting intact.

`WorkspaceTransactionsTest.absentMavenSourceRootsRemainPassiveAndCannotEscapeWorkspace` verifies configured directories need not exist on import and are not created as a side effect; the rest of that suite covers transactional preview/apply/undo and stale-source protection. `WorkerClientTest.namedModuleExecutionPreservesModuleIdentityAndFreshState` exercises an actual named-module program in an isolated JVM, including repeated runs with clean static state.

`MavenCompilationWorkspaceTest.failedOutputPublicationAndCancellationCannotReuseAnOldSuccessfulGeneration` forces a resource publication failure after bytecode generation, reverts the source, and checks that the old fingerprint cannot reuse partially replaced outputs. Cancellation invalidates the current published generation; an already pinned execution retains its original complete output throughout both failures.

CLI tests execute the entry point with machine-readable output. MCP tests exchange actual JSON-RPC JSON lines for initialization, discovery, inspection, preview, authorization, root restrictions, mutation and stale-plan rejection. The adapter uses the same headless engine and does not add a shell or Maven-goal execution tool.

## Reproduction

From the TurboJ checkout, with its required JDK and dependencies available:

```sh
./mvnw verify
```

The native/compiler/worker acceptance subset can be run separately:

```sh
./mvnw -pl core,worker,app,refactorj/refactorj-transactions -am test \
  -Dtest=MavenCompilationWorkspaceTest,WorkspaceTransactionsTest,MavenNativeAcceptanceTest,MavenAutoTestControllerTest,WorkerClientTest,FormattingControllerTest \
  -Dsurefire.failIfNoSpecifiedTests=false
```

The standalone MavenJ reactor has its own wrapper: run `./mvnw verify` from `mavenj/`. Network-policy tests bind only a temporary loopback server; a sandbox must permit that local socket. The lifecycle-parity fixture requires the pinned Maven plugins and JUnit dependencies in the checkout's local build repository for its explicit offline build. A missing prerequisite is a failed/missing verification, not a passing test.

The actual GUI smoke requires a graphical macOS session and a packaged application/test classpath. It is separate from headless Surefire tests. Inspect its report and screenshots after execution; successful compilation of `MavenSmoke` alone does not establish GUI acceptance. Benchmark commands, JVM flags, source counts and raw samples are in the linked performance reports.

## Compatibility boundaries still in force

Maven 3 effective-model behavior is implemented with official Maven components. Maven 4.1 model semantics are diagnosed rather than treated as Maven 3-compatible. Custom lifecycle plugins/extensions, generated build steps, resource filtering, custom Surefire/Failsafe providers and arbitrary fork settings require the explicit Maven lifecycle where the native path cannot reproduce them.

Ordinary compilation stays resident in the editor JVM, honoring `--release` and, where required, the selected platform image for source/target configuration. A different installed JDK is used for project execution and explicit processing/builds. Preview syntax from an older JDK requires an explicit matching-JDK Maven build. Named-module **program** execution is tested; named-module JUnit `--patch-module` behavior requires Maven Test and is not advertised as native parity.

For source/target 8, the current JDK's platform APIs remain visible, just as in Maven without `--release`; this is not Java 8 API or runtime compatibility. A selected Java 8 installation uses its bootstrap libraries. Source/target 8 with a different modular JDK requires an explicit Maven build because javac cannot apply `--system` below target 9. A model with unresolved configuration/JDK errors cannot publish runnable native output.

Source and Javadoc artifacts can be downloaded on demand through the configured Resolver policy. Quick Documentation currently reads Javadoc comments from source attachments and resolved signatures; a renderer for HTML inside Javadoc JARs is not implemented or claimed by this validation.

No Maven Central publication, clean-machine installer certification, arbitrary-project build parity or unmeasured performance claim follows from these tests.
