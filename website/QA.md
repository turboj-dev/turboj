# Website validation

The production build is the test target. Run with Node 22.23.4 or newer; this
machine also provides Node 26 at `/opt/homebrew/bin/node`.

```sh
npm run check
npm run build
npm test
npm run preview -- --port 4321
# In a second terminal, while preview is running:
npm run test:browser
npm run test:demo
node tests/session-browser.mjs
npm run test:themes
npm run test:spin
npm run test:scroll
node tests/theme-latency.mjs
npm run test:performance
```

The keyboard download is generated by the native `KeyboardRegistryAudit`, not
maintained as a second binding list. Asset preparation verifies every source and
generated-file SHA-256 in `docs/keyboard-reference-sources.json`, then copies the
inventory, active-profile reference and conflict report into `public/`. A stale
source or generated report fails the build. Regenerate the native audit after
native command/keymap changes; the website build itself never launches Java or
the application. `node scripts/export-keyboard-reference.mjs --check` verifies
the current public copies without rewriting them. The exporter tests exercise
drift rejection and the content test compares the production downloads with
the generated documents byte for byte.

Set `QA_BASE_URL` to test a different local preview URL. Set `CHROME_PATH` to an
existing Chromium or Chrome executable. The scripts do not download browsers.
Without an override, the scripts locate an installed Playwright Chromium,
system Chrome, or a cached Playwright headless shell. No username or workstation
path is embedded. `LH_RUNS=3 npm run test:performance` records three independent
Lighthouse runs, retaining every run rather than choosing the best result.

The content suite checks the approved English copy against generated HTML,
metadata, section targets, unavailable link suppression, and accurate values
from the available original application capture. That image records a 0.03 ms
cache hit, 1.17 ms execution, and 2.22 ms round trip. These are a single captured
application run, not website performance measurements or general Java benchmarks.

The browser suite checks widths 320, 390, 768, 1280, 1440, and 1920 pixels;
mobile navigation, Escape, anchor navigation, keyboard-operated FAQs, the
skip link, screenshot access, image loading, external requests and browser
errors. It saves desktop/mobile full-page screenshots and runs axe against
WCAG 2.2 AA tags with FAQ answers exposed. Results are written to
`artifacts/qa/`. Automated accessibility checks cannot prove complete WCAG
conformance; visual inspection and keyboard checks remain necessary.

The demo suite now checks the five-chapter native reconstruction against its
actual published checkpoints, including one real-time playback, independent
seeking, final-state hold, Replay, Pause/Resume, Skip, hidden/offscreen suspension,
keyboard controls, reduced motion and the native screenshot fallback with
JavaScript disabled. It checks lazy loading, stale chapter-load rejection and
bounded state across repeated chapter switches. The new evidence is written to
`artifacts/hero-story-qa/demo/`; historical `artifacts/demo-qa/` remains intact.
The source model tests enforce result boundaries without treating browser frame
timestamps as native compiler measurements.

Set `QA_ARTIFACT_ROOT=artifacts/hero-story-qa` for the common page, theme, theme-spin
and Lighthouse suites to keep new reports separate from historical output.
The production payload tests enforce 8 KiB gzip for the hero controller/model,
18 KiB for all emitted plus inline JavaScript, and 30 KiB for five lazy chapter
payloads. These are conservative asset-size accounts, not CDN transfer timings.

Lighthouse uses mobile emulation at 390 × 844, its default simulated mobile
network/CPU throttling, and the actual installed browser. JSON and HTML reports,
environment metadata, scores, LCP, CLS and TBT are written to
`artifacts/lighthouse/`. Local measurements do not represent hosting latency or
field Core Web Vitals. INP is not inferred from TBT or a navigation-only audit.
