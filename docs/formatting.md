# Java formatting in TurboJ

**Active engine:** google-java-format **1.37.0**, pinned in `app/pom.xml` and called in process through its Java
API.

**Default:** **IntelliJ IDEA**: IntelliJ's default code style on the bundled Eclipse JDT formatter (4 spaces, line
breaks kept as written). This is a product choice for now; among google-java-format's presets the comparison
recommends AOSP (see below).

**JavaFMT / FormatJ, TurboJ's own engine, is on hold.** Its code, tests and documentation stay in `javafmt/`. A
saved choice of it still works, but it is no longer offered and nothing falls back to it.

The full side-by-side comparison, generated by the engine itself, is in [formatting-comparison.md](formatting-comparison.md).

## Presets

| Preset | Engine style | Indent | Width | Kind |
| --- | --- | --- | --- | --- |
| **AOSP** (recommended among these) | google-java-format AOSP | 4 spaces | 100 | engine style |
| **Classic 80** | google-java-format AOSP, `maxLineLength(80)` | 4 spaces | 80 | TurboJ preset |
| **Wide 120** | google-java-format AOSP, `maxLineLength(120)` | 4 spaces | 120 | TurboJ preset |
| **Google** | google-java-format Google | 2 spaces | 100 | engine style |

**Google and AOSP are the engine's two styles.** Classic 80 and Wide 120 are TurboJ presets: the AOSP style with
another width. Every preset keeps google-java-format's K&R braces. Allman braces, tabs and other options are not
offered, because the engine cannot apply them.

Where to choose:
- **Code ▸ Formatter**, where google-java-format's presets come first and the other engines (Eclipse, IntelliJ
  IDEA, AWS Smithy) follow;
- **≡ ▸ General Settings…**, with a description and a live preview formatted by the engine.

The editor's indentation follows the preset. The choice is global (`config.json`: `formatter`, `tabWidth`). TurboJ
has no per-project formatter setting yet, so there is no project configuration to override.

## How it is integrated

- **The adapter** is `StandardFormatters.Google`, one class.
  - It uses `JavaFormatterOptions.builder().style(…).formatJavadoc(false).reorderModifiers(false)`.
  - The width comes from `JavaFormatterOptions.Style.toBuilder().maxLineLength(n)`, the API counterpart of the
    CLI's `--max-line-length`, both new in 1.37.0. Checked separately: the CLI lists `--max-line-length`, and the
    API has `Style.Builder.maxLineLength(int)`.
  - No wrapping is rebuilt by hand.
- **Layout only.** The adapter calls `Formatter.formatSource`, which, unlike the CLI's default pipeline, neither
  sorts nor removes imports and does not split long strings. Javadoc is not reflowed and modifiers keep their order.
  Organize Imports stays a separate, semantic action.
- **A selection** uses `formatSource(source, ranges)`: the engine formats the selected lines within the whole file,
  never the selection as a file of its own.
- **Off the EDT, never over newer typing.** `FormattingController` works on a snapshot and its version. The edits
  are computed on a worker thread and applied on the EDT only if the version still matches. Otherwise they are
  discarded (outcome STALE). The engine is created once per preset and reused.
- **One Undo step.** TurboJ turns the engine's output into the whitespace runs that changed, so the caret,
  selection and scroll position stay put. One ⌘Z restores the source and one ⇧⌘Z reapplies the formatting.
- **Errors.** A parse error leaves the document unchanged and shows the engine's diagnostic in the status line.
  There is no fallback to another engine.
- **Format on Save** (optional) saves the formatted text the editor shows, once.
- **Runtime.**
  - google-java-format uses the JDK's own parser, so the JVM must export six `jdk.compiler/com.sun.tools.javac.*`
    packages.
  - `./turboj` runs the jar, whose manifest declares `Add-Exports`.
  - The packaged app is started by jpackage's launcher with `-cp`, which ignores the manifest. So
    `scripts/package-macos.sh` passes the same exports as `--java-options`.
  - Tests get them through Surefire's `argLine`.
  - The packaged runtime includes `jdk.compiler` (jlink `--add-modules … jdk.compiler`).
  - Started without the exports, formatting reports "needs the JDK compiler exports" and leaves the file unchanged.

## What was verified

| Check | Result |
| --- | --- |
| Each preset uses its configured style, indent and width | `StandardFormattersTest.presetsUseTheEnginesOwnStylesAndWidths` |
| Idempotent | 40 of 40 corpus outputs; unit tests for all four presets |
| Output compiles with `javac --release 25` | 36 of 36 (the Spring example is formatted but not compiled: Spring is not on the classpath) |
| String and text block values unchanged | 40 of 40, comparing javac's literal values; unit test with a text block and a long string |
| Comments unchanged | 40 of 40 (text compared ignoring indentation, which the engine re-indents); Javadoc left as written |
| Imports unchanged | 40 of 40; unit test with unsorted and unused imports |
| Parse error leaves the document intact | `invalidJavaIsReportedAndLeftUnchanged` |
| Typing during formatting is never lost | `theRealEngineNeverOverwritesTypingAndUndoRedoAreOneStep`, with the real AOSP engine |
| Undo and Redo in one step | same test; `FormatterSmoke` in the real window (⌘Z, ⇧⌘Z) |
| Format on Save saves the shown version, once | `FormatterSmoke`: disk equals the editor, one "Saved" message |
| Packaged app | `package-macos.sh` built TurboJ.app; its runtime, with the launcher's `TurboJ.cfg` options, formats with all four presets |

Runtime support is not syntax support. The corpus checks syntax separately, with compact source files, instance
`main`, `import module`, flexible constructor bodies, record patterns, `switch` patterns and text blocks. All of
these are formatted and compile.

## Timings

Measured on this Mac (Apple Silicon, JDK 25.0.4.1) by `FormatterComparison`:

| File | Lines | First request, new engine | Next requests (median of 10) |
| --- | --- | --- | --- |
| first request in a fresh JVM | 19 | 118 ms | — |
| small (01_Grades) | 19 | 3–5 ms | 2–3 ms |
| medium (StandardFormatters.java copy) | 265 | 9–30 ms | 6–12 ms |
| large (TurboFrame.java copy) | 4788 | 71–146 ms | 53–74 ms |

The packaged app's runtime took 156 ms for its first request, then 2–3 ms. The first request loads
google-java-format and javac's parser. The range in each row is AOSP versus Classic 80, measured one after the
other, so it also includes JIT warm-up.

## What the comparison shows

Same corpus, ten examples, in [formatting-comparison.md](formatting-comparison.md):
- **Simple and didactic code** (Scanner, loops, records, switch patterns, text blocks, compact source files) comes
  out identical in the three 4-space presets: the width is never reached. Google differs only by its 2-space
  blocks.
- **Classic 80** gives the most classic look on simple code. It loses on modern Java:
  - Long concatenations go one operand per line: `toString` takes 8 lines.
  - `throws` and exception messages move to their own lines.
  - Nested lambdas form a staircase that breaks even `.equals(` and `System.out` / `.println`. Nine lines still
    exceed 80, because AOSP's 8-space continuation leaves no room.
- **AOSP 100** keeps those lines whole, puts builders and long annotated signatures one item per line, and breaks
  chains only when needed.
- **Wide 120** has the fewest lines and joins chains up to 112–119 columns. That is comfortable on a wide screen
  and less so in two side-by-side panels.
- **Google** fits nested lambdas best, because of its 2-space blocks and 4-space continuation. Its blocks are the
  least "Turbo".

## Limits

**Engine (google-java-format):**
- Two styles only, with fixed K&R braces.
- Continuation is twice the block indent: 8 spaces in AOSP, which compounds in nested lambdas.
- A binary expression that does not fit is split one operand per line.
- The width is a target: lines that cannot be broken can exceed it.
- No option to keep the user's line breaks.

**Integration:**
- The formatter choice is global, not per project.
- Comments are compared ignoring indentation, because the engine re-indents block comments: verified
  byte-for-byte only for literals.
- The Spring example is not compiled in the check.

## Recommendation among the google-java-format presets

TurboJ's default is IntelliJ IDEA's style for now. Among google-java-format's presets, **AOSP, four spaces, 100
columns** best keeps the clarity of a classic editor while staying comfortable for
everyday modern Java.
- Its four-space blocks give the Turbo look.
- It leaves lines whole where Classic 80 creates unnatural breaks (concatenations, nested lambdas).
- It stays readable in two side-by-side panels, unlike Wide 120.

**Classic 80** is the right choice for teaching and simple programs. **Wide 120** suits large application code on
a wide screen.

## Other engines

These stay available in Code ▸ Formatter:
- **Eclipse:** the IDE's built-in profile, with spaces.
- **IntelliJ IDEA:** its default code style reproduced on the Eclipse engine, because IntelliJ's formatter runs
  only inside IntelliJ.
- **AWS (Smithy):** the Eclipse profile AWS's Smithy projects enforce, Apache 2.0, bundled unchanged.

All three run on the bundled Eclipse JDT formatter.
