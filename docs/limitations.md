# Implementation status and limits

The desktop includes the shared semantic/refactoring workspace, CommandJ, in-process FormatJ and real JUnit execution. This document records boundaries that remain relevant to source correctness and host compatibility.

## Scope

- Multiple source buffers are retained during navigation, with one visible editor. MavenJ imports effective Maven models, profiles, dependencies, toolchains and reactor boundaries. Maven native compilation uses scoped classpaths/module paths and current dependent-module outputs, including unsaved buffers. Plain source files retain the lightweight single-file path. The application runs on Java 25; Maven projects retain their declared language/release configuration. Gradle import and ABI-level invalidation within a changed module remain outside this implementation. See [MavenJ compatibility details](../mavenj/docs/EFFECTIVE_POM.md).
- Inline completion, declaration navigation, Quick Documentation and parameter hints share JDT bindings. They are conservative on malformed or unresolved source; full IDE completion parity and automatic source downloads are not claimed. Javadoc is safe plain text, with paragraphs and tag content, rather than a complete HTML renderer. See [Java intelligence](java-intelligence.md) for source attachment and classpath setup.
- AI completion is optional and off by default. Context is limited to the current Java buffer, with bounded prefix/suffix and local declarations; project-wide context discovery is not implemented. Generated code can be wrong even when accepted by the insertion validator. Models are separately managed and are not bundled. Ollama, llama.cpp and OpenAI Responses have protocol tests; live model/account coverage is documented separately in the [AI validation report](ai-local-validation.md). Cloud use requires explicit source-sharing consent and macOS Keychain; live paid-cloud inference has not been verified. Secret detection is heuristic and cannot guarantee removal of every secret.
- JDT does a recovery-enabled full AST parse off the EDT; it is not a truly incremental parser. javac tasks use fresh compilation contexts with resident file managers. Passive analysis disables annotation processors; Maven projects have an explicit trusted isolated processor action. Arbitrary plugin transformations, old-JDK preview features and custom lifecycle behavior are diagnosed and require the appropriate real Maven build.
- JShell runs in the GUI bottom pane and CLI. Selection evaluation and AST-based statement evaluation are explicit actions; local variables inside an edited class are not automatically imported into JShell. JLine terminal editing and a JDI debugger remain later work. TurboTest runs real JUnit tests; Maven auto testing skips unchanged test-module generations and prioritizes prior failures and measured duration. A changed module may conservatively rerun its suite; method-level coverage-based impact selection and arbitrary Surefire/Failsafe provider parity are not claimed.
- Source names for unsaved public types are inferred from JDT. Multiple entry points have no selection dialog. Some inherited-main cases and unusual launch forms may need broader testing.
- Menus and internal panels are keyboard-navigable Swing surfaces styled by the current theme, including shortcuts, disabled items and selected states. The source surface is custom Java2D. DOS font fidelity, exhaustive accessibility, bidirectional scripts and complex grapheme clusters need further validation. Offsets are UTF-16; caret deletion preserves surrogate pairs, but the component is not a complete Unicode grapheme editor.
- The piece list is linear; highly fragmented documents and extremely long lines can cost more. The additions buffer is not compacted; undo retains at most 2,000 edits. Input is capped at 32 MiB per source file. Large pastes may still consume significant EDT time.
- Plain console pipes support Scanner/input; there is no PTY or ANSI terminal emulator. The GUI display is bounded to approximately 200k characters; each worker run defaults to 1 MiB output, 256 MiB heap and a 30-second execution budget, excluding blocked stdin waits. Worker API supports other limits; the GUI preferences do not expose them yet.
- Fast Run uses fresh class loaders in a reused JVM. It detects several global-state changes and lingering threads, but cannot reset every JVM-global state or native library. When process inspection is restricted it conservatively retires the worker. System.exit/Stop/timeout kill the process. Isolated Run is a process boundary, not a security sandbox. Programs retain the user's normal filesystem/network permissions.
- Atomic save checks external content before replacing; a narrow external-write race remains between check and replacement. Navigation retains unsaved buffers and undo, and Quit asks about each changed buffer. Crash recovery remains best-effort for the last active buffer; it does not restore all retained buffers or cursor/source-path metadata. Do not use concurrent TurboJ instances on the same recovery directory.
- Settings persist only a subset of the planned preference schema. No signing, notarization, updater or telemetry. Intel packaging is scripted but has not been validated on Intel hardware.

## Refactoring and external hosts

RefactorJ uses real semantic processors with conservative eligibility checks. Reflection, external binaries, dynamic class loading and generated sources can prevent static proof of safety. See the [operation-by-operation limits](../refactorj/docs/FEATURES.md) and [transaction recovery boundaries](../refactorj/docs/TRANSACTIONS.md). Native multi-file changes are journaled logical transactions, not filesystem-wide atomic commits.

IntelliJ and VS Code adapters are independently built and exercised in actual hosts; this does not establish compatibility with every IDE release. IntelliJ resource undo requires Local History. VS Code resource operations require saved affected files; undo restores editor text/path and a subsequent explicit Save persists it. See [adapter documentation](../refactorj/docs/ADAPTERS.md).

The performance reports distinguish measured paths from unmeasured targets. No comparison with other IDEs is claimed.
